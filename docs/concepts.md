# B3-1 개념 교재 — 웹 서버는 켜졌는데 왜 밖에서는 안 보일까?

> **읽는 법:** 이 문서는 용어 사전이 아닙니다. 한 가지 문제를 해결하다가 필요한 기술을 하나씩 만나는 이야기입니다. 각 장 끝의 **확인 질문**에 답할 수 있다면 해당 개념을 이해한 것입니다. 실제 배포는 [손으로 따라 하는 실습](deployment.md), 코드와의 대응은 [구현 해설](how-it-works.md)을 참고하세요.

## 0. 출발점: 내 노트북에 웹사이트가 있다. 다른 사람에게 보여주려면?

노트북에서 `http://localhost:80`을 열면 웹페이지가 뜬다고 가정해 봅시다. 친구에게 같은 주소를 보내면 왜 안 될까요?

`localhost`는 **각 컴퓨터 자기 자신**을 가리키는 이름입니다. 내 노트북의 localhost와 친구 노트북의 localhost는 서로 다른 컴퓨터입니다. 내 프로그램이 실행된다는 사실과 친구가 그 프로그램에 **접근할 수 있다**는 사실은 완전히 별개입니다.

이 문제는 네 가지 질문으로 나뉩니다.

1. **서버는 어디에서 실행할까?** → 항상 실행해둘 가상 컴퓨터 **EC2**.
2. **외부 사용자는 그 컴퓨터를 어떻게 찾을까?** → **퍼블릭 IP 주소**.
3. **인터넷과 서버 사이에 실제 길이 있는가?** → **VPC, Subnet, Route Table, Internet Gateway**.
4. **길이 있어도 누구나 들어올 수 있는가?** → **Security Group**, 그리고 서버 프로그램 **Nginx**가 요청을 받아야 함.

서버를 **만들 권한**까지 따져야 합니다. 이는 사용자의 네트워크 접속 권한이 아니라 AWS 자원을 생성·수정하는 **IAM** 문제입니다.

이 교재 전체를 관통하는 흐름:

```text
내 컴퓨터의 브라우저/curl
  └─ http://퍼블릭IP/health (HTTP 요청, TCP 80)
      └─ 인터넷
          └─ Internet Gateway (인터넷과 VPC의 출입구)
              └─ VPC / Public Subnet의 네트워크
                  └─ EC2의 Security Group (TCP 80 허용?)
                      └─ EC2 운영체제 / Nginx (정말 실행 중인가?)
                          └─ /usr/share/nginx/html/health
                              └─ HTTP 200 + "OK" 응답
```

> **비유는 이렇게까지만:** 퍼블릭 IP=건물 주소, 라우팅/IGW=도로, SG=출입문, Nginx=요청을 처리할 직원. IAM은 **건물을 만들고 관리할 수 있는 권한**입니다. 비유만 외우지 말고 실제 설정·파일과 연결해야 합니다.

## 1. EC2: 왜 내 PC가 아니라 클라우드 컴퓨터를 빌릴까?

### 1-1. 생겨난 이유

내 노트북을 서버로 쓰면 잠자기 모드에 들어가거나 집 인터넷 IP가 바뀌거나 전원을 끄는 순간 서비스가 끊길 수 있습니다. 외부 접속을 위해 가정용 공유기 포트 포워딩도 설정해야 합니다. 클라우드에서 **컴퓨터를 필요한 동안 빌려 쓰는 방식**이 이런 운영 문제를 줄입니다. AWS의 EC2(Elastic Compute Cloud)가 그 가상 컴퓨터입니다.

EC2는 '웹사이트' 자체가 아닙니다. **운영체제가 있는 빈 컴퓨터**에 가깝습니다. 여기에 프로그램을 설치하고 실행해야 합니다.

| 항목 | 개념 | B3-1에서의 모습 |
|---|---|---|
| EC2 instance | 실제로 켜지는 가상 컴퓨터 | `WebInstance`, `t3.micro` 1대 |
| AMI (Amazon Machine Image) | 시작할 때 복제할 OS 이미지 | Amazon Linux 2023 |
| EBS (Elastic Block Store) | 운영체제·파일이 저장될 디스크 | 암호화된 gp3 8GiB |
| SSH | 멀리 있는 컴퓨터에 명령을 보내는 보안 원격 접속 | `ssh -i ... ec2-user@퍼블릭IP` |
| Nginx | 브라우저의 HTTP 요청을 받아 파일을 응답하는 프로그램 | 포트 80에서 HTML과 `/health` 제공 |

예를 들어 **EC2를 생성만 하고 Nginx를 설치하지 않으면** 서버 컴퓨터는 켜져 있어도 HTTP 웹사이트가 있는 것은 아닙니다.

### 1-2. 컴퓨터를 만드는 것과 서비스를 켜는 것은 별개

일반 컴퓨터처럼 EC2에도 **하드웨어/가상머신 준비 → OS 부팅 → 프로그램 설치 → 프로그램 실행**이라는 단계가 있습니다. 이번 구현의 `UserData`는 첫 부팅 시 자동으로 Nginx를 설치하고 HTML 파일을 만들고 서비스 프로세스를 시작합니다.

```bash
dnf install -y nginx             # 패키지 관리자에게 Nginx 설치 요청
systemctl enable --now nginx     # 지금 시작하고, 다음 부팅 시에도 자동 시작
```

`dnf`는 Amazon Linux 2023의 패키지 관리 도구입니다. `systemctl`은 실행 중인 시스템 서비스의 상태를 다룹니다. `--now`가 없다면 자동 시작 설정만 하고 **당장 실행되지는 않을 수 있습니다**.

**질문:** EC2 상태가 `running`인데 `curl http://localhost`가 실패할 수 있나요? → 네. EC2와 Nginx의 상태는 다릅니다.

## 2. IP 주소·포트·URL: 사용자가 정확히 어디로 요청을 보내나?

### 2-1. IP는 컴퓨터(네트워크 접점)를, 포트는 서비스를 구분한다

웹 브라우저 주소창에 `http://203.0.113.10/health`를 입력했다고 합시다. `203.0.113.10`은 **설명용 예시 주소**이지 실제 배포 IP가 아닙니다.

- `http://`: 어떤 통신 규칙(프로토콜)로 대화할지.
- `203.0.113.10`: 어느 네트워크 목적지로 보낼지.
- `:80`: 그 컴퓨터의 어느 프로그램에 연결할지. HTTP의 기본 포트라 주소에서 생략할 수 있습니다.
- `/health`: 웹 서버에서 원하는 경로. 이번에는 같은 이름의 정적 파일입니다.

**하나의 컴퓨터에서 22번 포트는 SSH, 80번 포트는 HTTP**를 담당하도록 할 수 있습니다. 따라서 "서버에 들어갈 수 있다"는 표현은 불충분합니다. *어느 포트로, 어떤 목적의 접속*인지를 구분해야 합니다.

### 2-2. 사설 IP와 퍼블릭 IP는 왜 따로 있을까?

인터넷의 모든 기기에 전 세계 어디서나 도달 가능한 고유 IPv4를 무제한 줄 수는 없습니다. 그래서 회사나 클라우드 내부 네트워크는 `10.x.x.x` 같은 **사설 IP**를 사용합니다. 사설 IP는 인터넷에서 직접 목적지로 전달되지 않습니다.

이번 EC2는 VPC 내부 통신용 **사설 IP**와 인터넷에 공개할 **퍼블릭 IPv4**를 가집니다. 퍼블릭 IP가 할당되고 IGW 등 필요한 네트워크 조건을 갖추면 외부 통신이 가능합니다.

**중요한 함정:** 퍼블릭 IP가 있다는 사실 하나만으로 외부 접속이 보장되지는 않습니다. 경로와 보안 규칙, 서버 프로그램까지 맞아야 합니다. 자동 할당 퍼블릭 IPv4는 인스턴스를 중지했다가 시작하면 바뀔 수 있습니다.

### 2-3. CIDR: 범위를 숫자로 적는 방식

VPC 주소를 `10.0.0.0/16`, 서브넷을 `10.0.1.0/24`라고 적습니다. IP 주소는 32비트 숫자이고, **CIDR 뒤의 숫자는 앞에서 몇 비트를 네트워크 범위 지정에 고정하는가**를 뜻합니다.

| 표기 | 뜻 | 이번 실습에서의 역할 |
|---|---|---|
| `10.0.0.0/16` | 앞 16비트가 같은 큰 주소 범위 | 전체 VPC |
| `10.0.1.0/24` | 앞 24비트가 같은 더 작은 범위 | VPC 안의 Public Subnet |
| `내IP/32` | IPv4 주소 딱 한 개 | SSH 허용 대상 |
| `0.0.0.0/0` | IPv4 **전체** | HTTP 공개 대상 및 기본 라우트의 목적지 |

`/24`의 전체 주소는 256개지만 AWS가 일부를 예약하므로 EC2에 256개를 모두 배정하는 것은 아닙니다. 이 계산보다 중요한 것은 **서브넷의 주소 범위가 VPC 안에 들어가야 한다**는 점입니다.

**확인 질문:** `0.0.0.0/0`가 Route Table에 있으면 전 세계 사람이 SSH를 할 수 있나요? → **아니요.** Route Table의 의미와 SG의 포트 허용은 다른 판단입니다.

## 3. VPC → Subnet: 클라우드에서 왜 내 네트워크를 별도로 만들까?

### 3-1. VPC: EC2만 있으면 안 되나?

AWS에는 수많은 고객의 가상 컴퓨터가 있습니다. 어떤 주소 체계를 쓸지, 어떤 자원이 서로 네트워크로 통신할지 경계가 필요합니다. 그래서 **VPC(Virtual Private Cloud)**라는 논리적으로 분리된 네트워크를 만듭니다.

B3-1의 `LabVPC`는 `10.0.0.0/16` 범위를 소유합니다. 이 공간을 만들었다는 사실만으로 인터넷이 연결되지는 않습니다. **건물 부지를 정했다고 바깥 도로까지 생기지는 않는 것**과 비슷합니다.

### 3-2. Subnet: 왜 VPC 안을 다시 쪼개나?

실제 서비스에서는 외부 공개 웹 서버와 내부 전용 데이터베이스를 같은 방식으로 인터넷에 노출하면 위험합니다. 그래서 VPC 주소 범위를 여러 **서브넷(Subnet)**으로 나누고, 각각 다른 라우팅·접근 형태를 적용합니다. 서브넷은 한 **가용 영역(AZ)**에 속합니다.

이번은 필수 구현이므로 Public Subnet **한 개만** 만듭니다.

```text
VPC (10.0.0.0/16)
└─ Public Subnet (10.0.1.0/24)
   └─ EC2 + Nginx
```

**Public Subnet은 이름에 Public을 썼기 때문에 공개되는 것이 아닙니다.** 서브넷에 적용된 라우트 테이블에 **Internet Gateway로 향하는 경로**가 있어야 Public Subnet입니다. 서브넷이 퍼블릭이어도 그 안의 EC2에 퍼블릭 IPv4가 없으면 IPv4로 직접 외부 접근하기 어렵습니다.

**확인 질문:** VPC와 서브넷 생성이 끝났습니다. 이제 인터넷이 통할까요? → 다음 장의 두 부품이 필요합니다.

## 4. Route Table·Internet Gateway: 길이 없는 네트워크는 고립된다

### 4-1. Route Table은 무엇을 결정하나?

컴퓨터는 목적지 IP를 보고 **패킷**(네트워크로 보내는 데이터 단위)을 어느 방향으로 보낼지 결정해야 합니다. 그 규칙을 담은 표가 **Route Table**입니다.

이번 서브넷의 경로 표는 다음과 비슷합니다.

| 목적지 | 다음 대상(Target) | 뜻 |
|---|---|---|
| `10.0.0.0/16` | `local` | VPC 내부 주소로 보내면 내부로 전달 |
| `0.0.0.0/0` | `igw-...` | 그 밖의 IPv4 목적지는 인터넷 게이트웨이로 전달 |

`0.0.0.0/0`은 '모두에게 접근을 허용'이 아니라 **"더 구체적인 경로가 없다면 이쪽으로 보내라"**입니다. 이를 *기본 경로(default route)*라고 합니다.

한 주소가 두 경로에 모두 매칭된다면 일반적으로 **더 긴 접두사(더 구체적인 경로)**를 사용합니다. `10.0.1.5`는 `10.0.0.0/16`과 `0.0.0.0/0` 양쪽에 해당하지만 `/16`이 더 구체적이므로 `local`입니다.

### 4-2. Internet Gateway가 별도로 필요한 이유

VPC는 기본적으로 자체 경계를 가진 네트워크입니다. Internet Gateway(IGW)를 VPC에 **생성 및 연결(attach)**하고, 라우트 테이블에서 그 IGW를 **목적지(target)**로 선택해야 인터넷 방향이 열립니다. IPv4에서는 퍼블릭 IP ↔ 사설 IP의 주소 변환에도 관여합니다.

필요한 연결은 세 부분입니다.

```text
InternetGateway 생성 → GatewayAttachment로 VPC에 연결
                         ↓
PublicRouteTable: 0.0.0.0/0 → InternetGateway
                         ↓
PublicRouteAssociation: 위 표를 PublicSubnet에 연결
```

여기서 가장 많이 놓치는 것이 **라우트 테이블과 서브넷의 연결(association)**입니다. 경로를 정확히 만들었더라도 **다른** 라우트 테이블에만 들어 있으면 이 서브넷에는 적용되지 않습니다.

**확인 질문:** IGW는 붙어 있는데 EC2에서 `curl https://example.com`이 실패합니다. 다음 확인 순서는? → 서브넷에 *실제로 연결된* Route Table, 퍼블릭 IP, SG 아웃바운드, DNS 순서로 확인합니다.

## 5. Security Group과 IAM: '통과해도 되나?'라는 질문은 두 가지다

### 5-1. Security Group: 네트워크 통신의 경비

길이 있어도 모든 접속을 받아서는 안 됩니다. 실제 서버에 달린 **Security Group(SG)**은 IP 출발지·프로토콜·포트 단위로 통신을 허용하는 가상 방화벽입니다. SG는 기본적으로 **허용 규칙만** 정의하며 허용되지 않은 새 연결은 거절됩니다(대개 타임아웃으로 관찰).

| 방향 | 프로토콜/포트 | 허용 소스 | 왜 필요한가 |
|---|---|---|---|
| 인바운드 | TCP 80 | `0.0.0.0/0` | 웹사이트를 누구나 열도록 하는 미션 요구 |
| 인바운드 | TCP 22 | 현재 내 퍼블릭 IP `/32` | 서버 관리용 SSH를 내 장소에서만 사용 |
| 아웃바운드 | 필요한 인터넷 통신 | 기본 허용 | Nginx 패키지 설치, 외부 요청 검증 |

**인바운드(Inbound)**는 들어오는 새 연결, **아웃바운드(Outbound)**는 나가는 연결을 말합니다. SG는 **상태 저장(stateful)**이므로 허용된 연결의 **응답 트래픽**은 별도의 반대 방향 허용 규칙 없이 추적됩니다.

왜 SSH를 모두에게 열면 안 될까요? 웹 방문자는 HTML만 받아야 하지만 SSH로 로그인에 성공한 사람은 OS 명령을 실행할 수 있기 때문입니다. 따라서 TCP 22를 `0.0.0.0/0`로 열지 않습니다. 집·학교·VPN 환경이 바뀌면 *내 퍼블릭 IP도 달라질 수 있으므로* 현재 IP를 다시 확인해야 합니다.

### 5-2. IAM: 네트워크 접속이 아니라 AWS **자원을 조작**할 권한

혼동하기 쉬운 예:

- **질문 A:** 어떤 사용자가 `ec2:RunInstances`를 실행해 새 서버를 만들 수 있나? → **IAM**.
- **질문 B:** 브라우저가 이미 만들어진 서버의 TCP 80에 들어올 수 있나? → **SG**, 경로 및 서버 상태.
- **질문 C:** SSH로 OS에 실제 로그인할 수 있나? → **SG + SSH 키 + OS 계정**. IAM 권한만으로 SSH 로그인하는 것은 아닙니다.

IAM 정책은 크게 **Effect(허용/거부) → Action(어떤 API) → Resource(어떤 자원) → Condition(언제/어디서)**로 읽습니다. 예를 들어 `ec2:RunInstances`는 EC2 생성 API이고, `aws:RequestedRegion = ap-northeast-2`는 요청 리전을 제한합니다.

B3-1의 `iam/least-privilege-policy.json`은 AdministratorAccess를 부여하지 않고 EC2/VPC/CloudFormation 작업 범위를 제한하려는 실습 정책입니다. **다만 여러 EC2 API에 `Resource: "*"`가 있으므로 완벽하게 리소스별로 격리된 정책은 아닙니다.** 실습 전용 계정/환경에서 사용할 것을 권장합니다. AWS 콘솔에는 정책상 추가 조회 작업이 필요할 수 있으며, 배포 자체는 아직 실제 계정에서 검증하지 않았습니다.

**확인 질문:** 브라우저 접속이 막혔습니다. `AdministratorAccess`를 붙이면 해결될까요? → 네트워크 문제의 해법이 아니고 과도한 권한이므로 **안 됩니다**.

## 6. HTTP·Nginx·/health: 마지막 문을 열어도 직원이 없다면?

네트워크 설정을 모두 맞췄어도 Nginx가 꺼져 있으면 HTTP에 응답할 **프로그램이 없습니다**.

브라우저가 보내는 요청은 개념적으로 다음과 같습니다.

```http
GET /health HTTP/1.1
Host: <PUBLIC_IP>
```

Nginx가 `/usr/share/nginx/html/health` 파일을 읽으면, 기대 응답은 다음과 같습니다(아직 실제 실행 결과는 아닙니다).

```http
HTTP/1.1 200 OK

OK
```

- **HTTP 200:** 서버가 요청을 정상 처리.
- **HTTP 404:** 서버와 통신했지만 요청한 경로를 찾지 못함.
- **접속 시간 초과(timeout):** 서버에 도달하지 못했거나, 방화벽·경로·서비스 상태 등으로 시간 안에 연결이 성립하지 않음.
- **Connection refused:** 대상 호스트까지 연결 시도가 도달했지만 해당 포트에서 수신하지 않거나 명시적으로 거부됨.

**`/health`는 특별한 AWS 마법 API가 아닙니다.** 현재 구현에서는 텍스트 `OK`가 든 **정적 파일**입니다. Nginx가 요청을 제공한다는 간단한 확인일 뿐, 운영 서비스의 모든 내부 기능이 정상이라는 뜻은 아닙니다.

## 7. CloudFormation·UserData: 매번 수작업하면 왜 문제가 될까?

이번 실습을 콘솔에서 직접 만들어도 됩니다. 하지만 두 번째로 똑같이 만들어 보라고 하면 IP, SG, 라우트 연결 중 하나를 빼먹기 쉽습니다.

이를 줄이는 방식이 **IaC(Infrastructure as Code)** — 인프라를 코드로 선언하는 방법입니다. AWS의 **CloudFormation**은 `template.yaml`에 적힌 목표 상태를 읽고 여러 AWS 리소스를 생성합니다.

```yaml
PublicSubnet:
  Type: AWS::EC2::Subnet
  Properties:
    VpcId: !Ref LabVPC
    CidrBlock: 10.0.1.0/24
```

- `Type`: 어떤 AWS 자원인지.
- `Properties`: 어떻게 설정할지.
- `!Ref LabVPC`: 미리 생성한 VPC의 실제 ID를 사용. 실행하기 전에는 ID를 알 수 없으므로 참조가 필요합니다.
- `DependsOn`: 추론할 수 없는 선행 생성 순서를 명시.
- `Outputs`: 생성 후 퍼블릭 IP나 EC2 ID 같은 결과를 표시.

**UserData**는 인프라 정의와 조금 다릅니다. EC2가 처음 부팅될 때 OS 내부에서 실행할 초기 설정 스크립트입니다. "EC2 생성"과 "그 안에서 Nginx 설치"가 서로 다른 층이라는 사실을 코드로 보여 줍니다.

**중요:** CloudFormation의 `CREATE_COMPLETE`는 기본적으로 자원 생성 완료입니다. 이 템플릿에는 Nginx의 정상 준비를 기다리는 `cfn-signal` 구성이 없어서, **배포 성공으로 간주하면 안 됩니다.** 별도로 확인해야 합니다.

## 8. 세 종류의 테스트를 구분하면 장애를 찾아낼 수 있다

한 번에 외부 브라우저만 열고 성공/실패를 판단하는 대신 범위를 좁힙니다.

| 검사 장소 | 명령 | 어떤 층을 검사하나 | 성공했다고 알 수 **없는 것** |
|---|---|---|---|
| EC2 내부 | `curl -I http://localhost` | OS 내부 Nginx가 HTTP에 응답 | 외부 라우팅·SG |
| EC2 내부 | `curl -I https://example.com` | 외부로 나가는 DNS·경로·통신 | 외부에서 서버로 들어올 수 있는지 |
| 내 PC | `curl -i http://<PUBLIC_IP>/health` | 실제 외부 인바운드의 전체 경로 | 그 외 서비스 전체 상태 |

**생각 실험:** 첫 검사 성공, 두 번째 성공, 세 번째 타임아웃이라면? → Nginx 자체보다 *외부에서 서버로 들어오는 경로*를 먼저 봅니다. 퍼블릭 IP, IGW, 서브넷 연결 라우트, TCP 80 인바운드를 점검하세요. 반대로 첫 번째부터 실패한다면 Nginx 설치/실행 로그를 봅니다.

실전 조치와 증거 수집은 [문제 해결 가이드](troubleshooting.md)에 있습니다.

## 9. 삭제도 인프라의 일부: 컴퓨터를 껐는데 왜 돈이 나갈까?

클라우드는 요청한 자원을 **사용한 시간·양**에 따라 과금합니다. EC2 인스턴스를 종료(Terminate)하지 않고 단순히 **중지(Stop)**했다면 EBS 볼륨 등 일부 자원이 남을 수 있습니다. EC2가 켜져 있는 동안 퍼블릭 IPv4도 비용 대상이 될 수 있습니다.

이번 템플릿의 목표는 **EC2 1대·작은 EBS·퍼블릭 IPv4 하나**, 그리고 실습 종료 후 **CloudFormation 스택 삭제**입니다. 하지만 AWS 프리 티어 혜택은 **가입 날짜, 계정 플랜, 크레딧, 실제 사용량**에 따라 달라집니다. "micro니까 무조건 무료"는 틀립니다. 실습 전에 AWS Billing 화면을 확인하세요.

직접 콘솔에서 생성한 리소스는 **CloudFormation으로 관리되지 않습니다**. 그러므로 스택 삭제가 아니라 콘솔에서 직접 정리해야 합니다. 이 구분은 [실습 절차](deployment.md)와 [정리 체크리스트](cleanup-checklist.md)에 반영되어 있습니다.
